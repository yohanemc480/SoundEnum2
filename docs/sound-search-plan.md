## 目的と前提

Minecraftのサウンドを、名前の階層や再生時間だけでなく、実際の音の近さや特徴から探し、試聴してplaysoundコマンドを生成できるようにする。

CLAPを使用し、必要なPythonライブラリを導入する方針は決定済み。以下のタグ体系・検索仕様・ファイル構成は実装に向けた初期案であり、精度検証で調整する。計画時点では文書作成までとした。実装着手後の状態は上記の進捗に記載する。

- Pythonで音声解析と検索データ生成を事前実行する。
- Web側は生成済みの静的ファイルを読む。閲覧時のPythonサーバーやモデル推論は不要にする。
- 既存の階層選択・試聴・コマンド生成を維持する。再生時間の専用検索タブは削除し、類似音・タグ検索の時間条件へ集約する。
- UIは日本語のみ。表示文言は`Scripts/Text.ts`に集約し、キーをアルファベット順に並べる。
- CLAPのスコアを確率や正解率として表示しない。

## 提供する機能

### 1. 類似音検索

選択したサウンドIDを基準に、音が近いサウンドIDを一覧にする。結果から試聴・コマンド生成・別の音を基準にした再検索ができる。

- 初期表示順は類似度の降順。同点はサウンドID順に固定する。
- 基準サウンドID自身は除外し、同じIDを重複表示しない。
- 同じ音声を共有する別IDは残し、「同一音源」と区別できるようにする。
- 初期版は元音声に基づく検索とする。ユーザーが変更したピッチ・音量では検索結果を変えない。
- sound-events.jsonに設定されたピッチによる聞こえ方の違いも初期スコアには反映しない。原音ベースであることを表示する。

### 2. 自動タグ付け

固定のタグ一覧を用意し、各タグの説明文と音声のCLAPベクトルを比較する。タグは複数付けられる。自由なタグ名をモデルに生成させる方式にはしない。

| タグの軸 | 候補例 | 初期の扱い |
| --- | --- | --- |
| 音源・素材 | 金属、水、木、石、ガラス、声 | CLAPによる自動付与候補 |
| 動作・現象 | 衝撃、破壊、摩擦、爆発、足音 | CLAPによる自動付与候補 |
| 雰囲気・用途 | 不気味、穏やか、通知、魔法風 | 主観的なため試聴評価後に採用 |
| 音響的な性質 | 高い、低い、鋭い、響く | CLAPでの判別を検証し、必要なら別の音響特徴を併用 |
| 時間 | 短い、長い | 既存の秒数フィルターで扱い、自動意味タグと混ぜない |

日本語表示名と安定したタグIDを分離する。CLAPへの入力は英語の音の説明文を初期案とし、同じ意味の複数の説明文を比較・調整する。英語のUI対応は追加しない。

タグごとに閾値を持ち、閾値を超えたタグのみ付与する。必ず上位何個かを付ける方式は採らず、該当なしも許容する。スコア分布やタグ数が変わるため、全タグ共通の確率判定やsoftmaxの値だけで付与を決めない。

誤分類の補正は初期版では管理用JSONで行う。手動追加・手動除外を自動判定とは別に保存し、再生成で失わないようにする。矛盾する指定は生成時のエラーにする。ブラウザ上でのタグ編集は後続範囲とする。

### 3. タグ検索

タグを選択して一致するサウンドIDを表示する。

- 複数タグは初期版ではAND条件とする。タグ未選択では全件を対象にする。
- サウンドIDの部分一致検索と再生時間の範囲指定を併用できる。
- 時間条件は音声候補すべてが指定範囲に収まる条件にする。
- 通常のタグ検索はID順。類似音検索中のタグ絞り込みは類似度順を維持する。
- 選択中のタグ・検索件数・条件の解除操作を表示する。
- タグ候補は一覧から選択する。タグ名・別名による一覧の絞り込みは設けない。

任意の文章を入力してその場でCLAP検索する機能は初期版に含めない。静的サイトで実現するにはブラウザ推論または別の推論APIが必要になるため、別途設計する。

## 音声とサウンドIDの対応

解析単位は音声ハッシュ、検索結果の単位はplaysoundに使うサウンドIDとする。1つのIDに複数の音声候補があるため、この対応を明示的に生成する。

1. sound-events.jsonの文字列・オブジェクト形式を正規化する。
2. `type: event`参照を再帰的に解決する。循環参照・参照先欠落は報告する。
3. 音声名をaudio-file-hashes.jsonに照合し、IDから音声ハッシュ一覧への対応と逆引きを作る。
4. ピッチ・音量・重みは保持する。再生用の既存処理との対応をテストする。

初期のID間類似度は「双方の候補音声の組み合わせのうち最大のコサイン類似度」とする。意味は「似た候補音を含む」であり、ID内のすべての音が似ている保証ではない。平均ベクトル方式との試聴比較で、候補数の多いIDが過度に上位になる場合は再検討する。

タグ検索のAND条件は、同じ候補音声が選択したすべてのタグを持つ場合にIDを採用する。別々の候補にそれぞれ付いたタグを合算して、存在しない組み合わせを一致扱いしない。IDに表示するタグは候補の和集合とし、一部候補だけのタグは区別する。

結果には一致した音声候補を保持し、その候補を固定して試聴できるようにする。現行`SoundManager.Play()`は候補をランダムに選ぶため、検索で一致した音を聴ける再生経路を追加する。生成コマンドはサウンドIDを使い、ゲーム内の候補選択を固定できるとは表示しない。

## データ構成案

| ファイル・場所 | 役割 |
| --- | --- |
| `tools/requirements-clap.txt` | 検証後のPython依存関係を記録 |
| `tools/build_similarity.py` | 音声特徴と類似度生成。共通部分は後述のタグ生成から利用可能にする |
| `tools/build_tags.py`（追加予定） | テキスト特徴抽出、タグ判定、手動補正の適用 |
| `tools/sound-tags.json`（追加予定） | タグID、表示文言キー、説明文、軸、閾値 |
| `tools/sound-tag-overrides.json`（追加予定） | ハッシュごとの手動追加・除外タグ |
| `.cache/clap/` | モデルと正規化ベクトル。Web配信・Git管理対象外 |
| `resource/{version}/similarity.json` | 現行のハッシュ別近傍一覧。単独では複合絞り込みの完全な検索には不足 |
| `resource/{version}/audio-tags.json`（追加予定） | 音声ハッシュごとのタグ判定、生成メタデータ |
| `resource/{version}/audio-embeddings.bin`（追加予定） | 全件の正規化ベクトル。ブラウザで絞り込み後の類似度を計算する用途 |

ベクトルの行順と次元、バイト形式はsearch-indexに記録する。初期案はlittle-endianのFloat32で、音声数×次元数×4バイトの容量を見積もる。実測して配信容量が大きければ分割読み込みや量子化を検討する。

上位20件だけを絞り込む方式では、21位以下にあるタグ一致音を見落とす。複合検索はタグ・ID・時間条件で候補を絞ってから全候補を採点し、結果件数に制限をかける。全ベクトル方式の負荷が許容できない場合は仕様を再検討し、結果が完全でない検索を黙って提供しない。

生成物にはschemaVersion、Minecraftバージョン、モデルID・revision、前処理バージョン、タグ定義のハッシュ、入力ファイルのハッシュを記録する。異なるモデルや前処理のベクトルを混用しない。現在の`embeddings-v1`のみのキャッシュ識別はこの情報を含む方式に改める。

## Python側の処理

1. Python・PyTorchの対応とパッケージ取得先への接続を確認し、仮想環境への導入失敗を切り分ける。
2. 少数音声でモデル取得・OGG読み込み・モノラル化・リサンプリング・特徴抽出を通す。
3. 長さゼロ、無音、非有限値、長い音声、サンプルレート違いを確認する。
4. 音声とテキストを同じCLAPチェックポイントの対応する投影空間で特徴化する。現在の音声モデルだけの読み込みではタグ説明文を処理できないため、テキスト側を追加する。
5. 正規化後にコサイン類似度を計算し、タグごとの閾値と手動補正を適用する。
6. IDとの対応・検索用データを生成し、検証後に公開対象へ反映する。

中断後の再開、同一入力での再現性、キャッシュの破損検出を整備する。モデルrevisionと検証済み依存バージョンを固定し、必要な乱数シードも固定する。

複数出力ファイルは一時領域に全件生成して整合性を確認後に切り替える。索引とベクトルはバージョン直下のtags.json・audio-embeddings.binへ保存し、一緒に公開する。読み込み時はベクトルのハッシュで組み合わせを検証する。バージョン指定の更新コマンドからCLAP解析まで実行する。新バージョンの検索データがない場合は検索UIで案内する。

## Web側の構成案

- `WorkerSearchService`：索引・ベクトルの遅延ロード、ハッシュと形式の検証、再試行。
- `SoundSearchEngine`：タグ・ID・時間条件、ID単位の重複排除、順位付け。DOMから分離する。
- `SoundSearchBrowser`：検索条件と結果表示、ページ切替、基準音の変更。
- 共通の試聴処理：候補指定再生と既存ランダム再生、コマンド表示、履歴登録を一貫させる。

タブ切替は`BrowserTabs.js`で共通化済み。再生時間専用画面とその実装は削除済み。`SoundResourcePaths`に検索データの参照を追加する。

索引とベクトルは検索画面を開いた時に読み込み、必要なら計算をWeb Workerに移す。古い検索要求の結果で新しい条件の画面を上書きしない。読み込み表示の領域を確保し、レイアウトのずれを避ける。取得失敗・対象なし・データ未生成を別の状態として扱う。

## 検証方針

### 自動検証

- 同じベクトルの類似度がほぼ1になり、自己IDが結果から除外される。
- 複数候補・共有音源・入れ子のevent参照で対応と重複排除が正しい。
- 違う候補に分散したタグをAND一致として扱わない。
- 事前近傍20件の外にある条件一致音も検索できる。
- 手動除外が自動付与に優先し、未定義タグや矛盾する補正は検出される。
- モデル・前処理・タグ定義変更で必要な部分だけ再生成される。
- 欠落データやハッシュ不一致で誤った検索結果を表示しない。

### 試聴・操作検証

代表的な基準音20件程度について上位10件を試聴し、「似ている／用途が近い／無関係」を記録する。タグは付与された音だけでなく、付与されなかった候補も確認して誤付与と見落としを評価する。閾値調整用と確認用の音声を分ける。

品質の合格値はまだ未確定。まず結果を記録して採用タグを絞り、確認用データでの精度を見て公開対象を決める。特に「魔法風」「不気味」などは正解を断定せず、検索に役立つかを評価する。

実際の件数で、初回ロード容量・検索応答時間・メモリ使用量・全件生成時間を測る。ページ操作や試聴が止まらないこと、連続検索・ロード失敗時の再試行・キーボード操作も確認する。

## 後続で判断する事項

- 採用するタグ一覧と各閾値。
- 最大類似度方式と平均ベクトル方式の品質差。
- 長い音声の平均化で失われる特徴への対応。
- sound-events.jsonのピッチを反映した追加解析の必要性。
- 全ベクトルの配信容量とブラウザ計算時間に応じた圧縮・分割。
- OR・除外タグ、ブラウザ上のタグ編集、自由文による意味検索の追加。

最初の着手点は段階1。環境復旧と実音声での推論が通るまでは、CLAPの出力品質を前提にタグ数や閾値を確定しない。
